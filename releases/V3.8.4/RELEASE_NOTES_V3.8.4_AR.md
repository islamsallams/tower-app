# إصدار V3.8.4 — توضيح تعثر إرسال إشعارات الجهاز

نتيجة المستخدم من القاعدة أظهرت test بحالة PENDING ومحاولة واحدة وtrip بحالة PENDING ومحاولتين، وكلاهما last_code=0. هذا يثبت تسجيل المحاولة دون تسجيل رد HTTP؛ لا يثبت وصولها للمزوّد أو الجهاز، ولا يحدد سبب الاستثناء.

كان مسار V3.8.3 يحوّل الاستثناءات إلى إعادة محاولة برقم صفر دون تمييز. أصبح يسجل مرحلة التوقف برقم مختصر آمن، ويعرض نتيجة آخر إرسال في بطاقة الجهاز عند «تحديث الحالة»؛ لا حاجة لاستعلام SQL لقراءة النتيجة الجديدة. الإشعار المفعّل يعني وجود اشتراك فقط، وSENT تعني قبول المزوّد، وليست تأكيد استلام الموبايل.

الرموز الجديدة: -11 تحقق صلاحية المستلم، -12 بيانات الاشتراك، -13 تجهيز المحتوى، -14 تشفير الرسالة، -15 توقيع الطلب، -16 اتصال المزوّد، -17 انتهاء مهلة الاتصال. سجل Worker يضم المرحلة والرمز ورمز قاعدة مسموحًا به عند وجوده، دون الرسالة أو عنوان الاشتراك أو مفاتيح أو نص الاستثناء. الردود HTTP تبقى بأرقامها الأصلية.

لا SQL جديد. ارفع ZIP V3.8.4 وحدّث الصفحة بالكامل. من حساب الأمين المفعّل على الموبايل، وبعد دقيقة من آخر تجربة، اطلب إشعار تجربة واحدًا، ثم حدّث حالة الجهاز وصوّر نص آخر إرسال. الفشل السابق برقم0 لا يتغير بأثر رجعي؛ السبب الجديد يحتاج محاولة جديدة. لا تغيّر أذونات الهاتف عشوائيًا بناء على PENDING وحدها.

هذه دفعة تشخيص وعرض، وليست إثبات إصلاح السبب النهائي أو وصول الإشعار للموبايل. لم تتغير شروط إعادة المحاولة أو الاشتراك أو مفاتيحه أو إذن المستخدم أو محرك المشاوير أو أي حسابات وتقارير وPDF. لم يُرسل إشعار فعلي في فحوص المساعد ولم ينشر Cloudflare أو يشغل SQL حيًا.
