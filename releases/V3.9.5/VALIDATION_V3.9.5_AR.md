# تحقق V3.9.5

فحوص آلية محلية من الكود الحالي، بلا تشغيل بيانات حقيقية أو إرسال خارجي:

- PostgreSQL محلي عبر PGlite: إعادة تثبيتSQL، رفض العضوية وصلاحياته، معاينة التمويل والتقريب وحقوق الرد وحماية إعادة التنفيذ وتغير السداد والتراجع الذري، وإشعارات التسويات وإسقاط Telegram حسب المستلم.
- نموذج DOM/history يشغل الدوال الفعلية: نافذة الرفض مع حدث Back غير المتزامن، إلغاء السبب، تحديث عنوان التاب وعزل الحساب، حفظ المبلغ عند فشل المعاينة وزر نسخ موجود، وإبطال المعاينة بتغيير المبلغ وروابط Telegram.
- Worker مع اعتراض كل HTTP: صلاحيات التمويل والرفض، رسالة خطأ حماية التحديث الآمنة، مثال وحدة26 بإجمالي42 وبند غير مسعر، إخفاء القيم، الاعتماد والتراجع، الزر المباشر، وإلغاء الإرسال عند تغيير الربط.
- فحوص ثابتة للوظائف المستقرة مقابل SOURCE394: محرك المشاوير والتسويات والأتعاب وحفظها، مهام التحصيل والاستلام والأقساط والردود، PDF والتقارير والنسخ والاستعادة والتصفير، وكلSQL السابق بايت ببايت.
- فحوص SQL مستقلة موجودة مسبقًا للتسويات ومدفوع الاعتماد والتراجع، والخدمات الدورية والتصفير الاختياري، تعمل بالتوازي مع فحوص الدفعة.
- Android: بناء وتوقيع، Lint، سياسات تحديث على JVM، نموذج الربط الأصلي، ثم فحص نسخةAPKوشهادتها ومحتوياتها والإصدار.
- الحزم: CRC، تطابق التشغيل والمصدر وpublic، حفظ كل مسارات المصدر السابق، عدم نشر أسرار أو ملفات توقيع أو SDK، وبصمات ملفات التسليم.

تشغيل بوابة الفحص من جذر المصدر: python3 tools/check_release395.py. يلزم Node ومكتبتا @electric-sql/pglite وlinkedom؛ يحدد TOWER_PGLITE_MODULE وTOWER_DOM_MODULE مساريهما. الفحوص مستقلة وتعمل بأربعة مسارات متوازية؛ أي فشل يمنع الاعتماد. سجلاتها الخام في مجلد مؤقت خارج الحزم.

حدود الدليل: امتداد حماية التحديثات المستخدم في Supabase غير متاح داخل PGlite؛ فحصنا شرطWHEREفي الدالة المنشورة ونتائجها المالية، ولا نزعم محاكاة بيئة الإنتاج بكل إعداداتها. الخلل تحدد من رسالة السجل الفعلية UPDATE requires a WHERE clause. لا اختبارات متصفح/هاتف أو وصول فعلي لTelegram، ولاSQLحي أو نشرCloudflare. اختبار شاشة لا يثبت إرسالًا، ونجاح تجهيز الطابور لا يثبت وصول الرسالة للجهاز.
